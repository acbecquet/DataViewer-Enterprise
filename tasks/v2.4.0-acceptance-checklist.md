## 1. DATAVIEWER-3 - TPM upload actually persists
*Was: uploads silently saved nothing since ~Jun 1 - the live DB was missing the `puffing_regime` / `raw_grid` columns and the error was swallowed.*
- [ ] First launch against the live NAS: the app log `dataviewer.log` shows a one-time `ensureSchema: added missing column ...` line (the self-heal). Later launches do not repeat it.
- [ ] Load the TPM `.xlsx`. It loads with no upload error; the DB sync indicator shows saved (not failed).
- [ ] Press **Ctrl+U** (Update Database) on the loaded file -> succeeds; **no** `column "puffing_regime" does not exist (42703)` error.
- [ ] Reload the same file from the database (or relaunch the app) -> the rows are present. The upload truly persisted.
- [ ] Offline: with the NAS unreachable, loading still works read-only and the app does not crash; on reconnect the data persists.

## 2. DATAVIEWER-4 - sensory scores are the single source of truth (live + responsive)
*Was: live edits could reset to 5 or be clobbered by a whole-session overwrite; exports and closing used stale values.*
- [ ] Open a sensory session and adjust several panel scores - input feels instant, no lag while typing or selecting.
- [ ] **Two-client live check:** open the same session on the second client. Edit a score on A -> B reflects it within ~1s, and **other cells do NOT reset to 5**.
- [ ] Edit several scores, then **Save** -> reopen the saved `.xlsx` and reload from the DB: both show your **latest** scores, not stale ones.
- [ ] Without pressing Ctrl+U, generate a **report** and/or an **Excel export** -> it uses the live / DB-authoritative scores, not stale in-memory values.
- [ ] Edit scores, then **Close the session with the toolbar Close button** -> reopen -> every edit is persisted (Close flushes first; nothing lost).
- [ ] **Ctrl+U** still works, does not stutter, and does not wipe live scores.

## 3. DATAVIEWER-4 - same guarantees in Detailed Sensory
- [ ] Repeat the section-2 checks in **Detailed Sensory** (14-question form, dual radar charts).
- [ ] After Save, confirm any **sample images and metadata are still intact** (not dropped by the save).

## 4. Zero-Save-As - no Save-As dialogs anywhere in sensory / detailed
*New: Save auto-names from test + tester (+ round) into the default folder; the only guard is "test name + tester required".*
- [ ] Sensory, Test Title + Tester filled -> click **Save**: **no Save-As dialog**; a file auto-appears in the default save folder (named test + tester + round) and the session is in the DB.
- [ ] Detailed Sensory -> **Save**: same - no dialog, auto-named file in the default folder + DB.
- [ ] Clear the **Test Title** (or **Tester**) and click Save / Update -> **blocked** with a clear "enter a test name and tester" message; nothing is saved.
- [ ] Brand-new unnamed session with a few scores: wait ~5s (autosave) -> **no dialog, no nag, no stutter** - autosave silently skips an unnamed session.
- [ ] Try to **Close** an unnamed session that has data -> it refuses / tells you to name it (no silent loss). Name it, Close -> it persists.
- [ ] Sanity: there are now **zero** "Save As" pop-ups in the sensory and detailed flows.

## 5. DATAVIEWER-2 - sample-name dropdown scoped to the current test
*Was: the dropdown listed every sample name ever saved (a global pool), growing until it covered the screen.*
- [ ] With a Test Title set, open a sample card's sample-name dropdown -> only that test's sample names, and the popup is **height-capped** (scrolls; never fills the screen).
- [ ] Switch the Test Title -> the dropdown shows that test's names (or empty if none yet).
- [ ] Clear the Test Title -> the dropdown is **empty** (not the old global flood).
- [ ] **Backfill:** open an OLD test that had sample names before this build -> its historical names appear (the one-time backfill seeded them).
- [ ] Save a new sample name under a test -> reopen -> it shows scoped to that test.

## Good to know while testing
- **Mixed-version blip (expected, harmless):** during the ~1h auto-update window, a client still on an older build may log a `42P10` when it writes to the sample-name preset pool (a side effect of the DV-2 index swap). Session data is unaffected and it clears once that client updates. This is **not** a v2.4.0 defect.
- **No manual SQL:** the schema self-heals on the first v2.4.0 connect - nothing to run on the NAS.
