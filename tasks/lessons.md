# Lessons Learned

## 2026-03-19: Sensory layout should be horizontal, not vertical
- **Mistake:** Set sensory panel splitter to `Qt::Vertical` (cards top, chart bottom) matching the TPM layout
- **Correction:** Sensory mode uses a **horizontal** layout — cards on the left, radar chart on the right. This is intentionally different from TPM mode (table top, plot bottom).
- **Rule:** Don't assume new UI modes should mirror existing layout orientations. When the user says "place data and plot in the space where table and chart are," the spatial arrangement can still differ.

## 2026-05-11: QSqlDatabase reference release on Windows
- **Discovery:** Calling `db.close()` alone is insufficient on Windows — the file handle isn't released until `QSqlDatabase::removeDatabase(name)` is called. When the Qt documentation warns "connection still in use", assigning `db = QSqlDatabase()` first prevents the warning.
- **Applied in:** `PostgresConnection::close()`, `PostgresConnection::open()` (connection cycling), and `MigrationTool::finalizeSource()` (SQLite close after reading source).
- **Rule:** Always call `QSqlDatabase::removeDatabase()` when closing a database for the last time, or clear the object reference first.

## 2026-05-11: QTemporaryFile blocks QFile::rename on Windows
- **Discovery:** Even after explicit `close()`, `QTemporaryFile` retains a file-share flag that prevents `QFile::rename()` on the same object. The file is not fully released to other processes until it goes out of scope.
- **Applied in:** `tst_migrationtool` — tests that rename files should use a plain path under `QDir::tempPath()` instead of `QTemporaryFile`.
- **Rule:** For tests that need atomic file operations (create temp, rename to final), avoid `QTemporaryFile`; use explicit temp paths and manual cleanup.

## 2026-05-11: MIP/AIP source-file mitigation
- **Discovery:** Every new `.cpp`/`.h` file in this repo may inherit Microsoft Information Protection (MIP) sensitivity labels at rest, causing build tools (`g++`, `head`, `cat`) to see ciphertext (`%TSD-Header-###%...`). The Python interpreter is on the MIP allowlist and reads plaintext.
- **Applied in:** All file creation in Plan A — write new source files via Python's delete-and-rewrite pattern (see CLAUDE.md section "File creation convention"), not via the Write tool. Before any C++ build, run `python tools/decrypt_via_copy.py --apply` to strip labels.
- **Rule:** New `.cpp`/`.h` files must be written via Python. Subagents that produce source code must include the deletion pattern. The decrypt script is idempotent and runs as a build pre-step until labels stabilize.

## 2026-05-11: postgres:16 doesn't bundle pg_cron
- **Discovery:** The official Docker image for `postgres:16` does not include the `pg_cron` extension. Container startup fails on `CREATE EXTENSION pg_cron` with "could not access file pg_cron".
- **Applied in:** `deploy/postgres/Dockerfile` — derived image installs `postgresql-16-cron` from the PostgreSQL Development Group (PGDG) repository before initializing the database.
- **Rule:** When using a postgres Docker image, always derive a custom image for any non-bundled extensions (`pg_cron`, `pg_partman`, etc.). The Dockerfile pattern is: `FROM postgres:16 && apt update && apt install -y postgresql-16-<extension> && ...`.
## 2026-05-28: VBA/COM worksheet copy — capture by name-diff, never by position/ActiveSheet
- **Discovery:** Seeding the post-upload reset snapshots failed two ways that silently corrupted the workbook. (1) `Worksheet.Copy After:=Worksheets(Count)` when the last sheet is **very-hidden** (`_Template_Master`) misplaces the copy, so capturing the new sheet by position grabbed a pre-existing sheet and `snap.Name = ...` renamed it 12 times (only `_Template_11` survived; `_Template_Master` was clobbered). (2) In pywin32, `ws.Copy(After=anchor)` as a **named** arg doesn't bind in late-bound COM and silently spawns a throwaway workbook (0 sheets added to the target).
- **Applied in:** `excel-sidecar/DataViewerUpload.bas` — `AddSnapshotFrom` and `RestoreSheetFromTemplate` copy after/before a **visible** anchor (the "DataViewer Upload" sheet / the live sheet), find the new sheet by **name-diff** (record sheet names before the copy), and never `Delete` the original until the replacement is confirmed present. Recovery COM scripts pass the anchor **positionally** as `Before` (`ws.Copy(beforeSheet)`), not `After=`.
- **Rule:** When copying sheets in VBA/COM: (a) never anchor Before/After on a very-hidden sheet; (b) capture the new sheet by name-diff, not `ActiveSheet` or `Worksheets(Count)`; (c) make any replace transactional — copy first, confirm, then delete; (d) in pywin32 pass `Copy`/`Move` anchors positionally, not as `After=`. Separately: an over-strict guard (snapshot `A1` must equal the live sheet's `A1`) false-skipped a sheet whose template title legitimately differed ("Lifetime Test 2") — prefer a robust structural invariant over brittle equality.

## 2026-05-29: Never reuse a color within a plot
- **Discovery:** Plot palettes were small fixed arrays indexed with `% N`, so colors repeated once the series count exceeded the palette — the Lifetime comparison chart read as "only blue and orange," and 7+ files wrapped hues back to blue. The same `% N` flaw existed in `PlotEngine`, `PlotWidget`, and `RadarChartWidget`.
- **Applied in:** New `AppTheme::seriesColor/seriesColors/shade` (single source of truth, reusing the radar chart's already-vetted no-yellow palette + golden-angle generation past 20). All report charts, GUI plots, and radar overlays route through it; the `ReportGenerator` comparison chart stays grouped by file via distinct base hues + `shade()` per sample.
- **Rule:** Never `palette[i % N]` in a plot — size the palette to the element count via `AppTheme::seriesColors(n)` / `seriesColor(i)` (or `shade()` for grouped charts). No yellow (hue ≈ 45°–70°); keep series saturated and mid-dark — yellow and pale/light colors wash out on projectors.

## 2026-05-29: Repurposing a positional column — audit EVERY consumer, not just the obvious ones
- **Discovery:** Making per-row data-table column index 4 dual-purpose (Resistance double ↔ Puffing Regime string, v2.2.1) required touching far more than the read/write/display path. A non-obvious consumer — the live multi-user conflict "take their value" tooltip (`MainWindow::handleRemoteRowChange`) — used a hardcoded 12-column positional `SELECT ... resistance ...` and stamped values by visual column index, so accepting a remote regime edit silently overwrote the regime with resistance. Per-task reviews missed it (it wasn't in any task's scope); only the whole-feature integration review caught it.
- **Applied in:** `liveColumnForDataCol`/`dataColForLiveColumn` (sheet-aware col↔DB-column map) cover the LiveSync paths; `handleRemoteRowChange` now fetches `puffing_regime` and stamps it into col 4 when `sheet->hasPerRowRegime`. `DataRow` keeps BOTH `resistance` and `puffingRegime`; the per-sheet `SheetResult::hasPerRowRegime` flag drives all branches.
- **Rule:** When a positional column/index changes meaning, grep the WHOLE repo for EVERY positional consumer of that index/field/DB-column (SELECT column-lists, `value(N)`, index-based stamps, write-back arithmetic, conflict/tooltip paths), not just the obvious populate/edit/save. A final cross-task integration review is where these between-the-cracks consumers surface — do it.

## 2026-06-05: A spec-conformance audit can't catch a spec that doesn't match intent
- **Mistake:** Plan C (auto-recovery) was brainstormed, built, audited (5 parallel auditors), and shipped as v2.3.0 scoped as **crash-only** recovery — it deliberately cleared the snapshot on a clean/declined close and only offered to restore after a crash/update. The user's very first real test ("opened files, closed, said *don't save*, then nothing to reload") exposed that they actually wanted **restore-my-last-session**: persist the snapshot across *any* close and auto-offer to reopen (files + unsaved edits) on *every* launch. The deep audit passed because it verified the code against the (mis-scoped) spec — conformance ≠ correctness of intent.
- **Root cause:** Brainstorming locked "clear on clean close" + "crash detection" as decisions without surfacing the one UX fork that actually mattered: *does a normal/declined close discard the session, or should it always be restorable next launch?* That question was never put to the user.
- **Applied in:** v2.3.1 — `closeEvent` finalizes via `flushNow(true)` instead of `clear()`; the launch prompt auto-offers on any prior session and **lists the item names**; restore includes unsaved edits; DB-loaded files are snapshotted; "No" keeps the session retrievable (no accidental-dismiss data loss).
- **Rule:** For any "don't lose my work" / recovery / session-restore feature, explicitly ask the user the close-behavior fork up front (clean/declined close = discard vs. always-restorable?). And never treat a passing spec-audit as proof the feature is right — for user-facing behavior, verify against the user's actual goal with a quick real run (or have them try it) *before* calling it done, because an audit only proves the code matches the spec, not that the spec matches what they wanted.

## 2026-05-29: Ephemeral test Postgres applies init.sql's base block only — not migrations
- **Discovery:** `tests/start-test-postgres.ps1` applies only the `BEGIN..COMMIT` block of `init.sql`, NOT the files in `deploy/postgres/migrations/`. So DB tests that exercise migration-only schema (e.g. sensory header presets from `2026-05-20-sensory-header-presets.sql`) FAIL against the ephemeral container (`saveSensoryHeaderPresets`/`saveSensoryLayout` return FALSE) — a pre-existing, environmental failure unrelated to whatever feature is under test.
- **Applied in:** The v2.2.1 `data_rows.puffing_regime` column was added to BOTH `init.sql` (base block) AND a migration file — so the ephemeral container has the column and `perRowRegime_roundTrip_newAndOld` passes. The migration is only for already-deployed DBs.
- **Rule:** A new column/table must go in `init.sql`'s `BEGIN..COMMIT` block (fresh installs + the test container both read it), with a separate migration file ONLY for upgrading deployed DBs. When triaging `tst_databasemanager` failures against the local container, first check whether the failing feature's schema lives only in a migration.
