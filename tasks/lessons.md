# Lessons Learned

## 2026-03-19: Sensory layout should be horizontal, not vertical
- **Mistake:** Set sensory panel splitter to `Qt::Vertical` (cards top, chart bottom) matching the TPM layout
- **Correction:** Sensory mode uses a **horizontal** layout — cards on the left, radar chart on the right. This is intentionally different from TPM mode (table top, plot bottom).
- **Rule:** Don't assume new UI modes should mirror existing layout orientations. When the user says "place data and plot in the space where table and chart are," the spatial arrangement can still differ.

## 2026-05-11: QSqlDatabase reference release on Windows
- **Discovery:** Calling `db.close()` alone is insufficient on Windows — the file handle isn't released until `QSqlDatabase::removeDatabase(name)` is called. When the Qt documentation warns "connection still in use", assigning `db = QSqlDatabase()` first prevents the warning.
- **Applied in:** `PostgresConnection::close()`, `PostgresConnection::open()` (connection cycling), and `MigrationTool::finalizeSource()` (SQLite close after reading source).
- **Rule:** Always call `QSqlDatabase::removeDatabase()` when closing a database for the last time, or clear the object reference first.

## 2026-05-11: QTemporaryFile blocks QFile::rename on Windows
- **Discovery:** Even after explicit `close()`, `QTemporaryFile` retains a file-share flag that prevents `QFile::rename()` on the same object. The file is not fully released to other processes until it goes out of scope.
- **Applied in:** `tst_migrationtool` — tests that rename files should use a plain path under `QDir::tempPath()` instead of `QTemporaryFile`.
- **Rule:** For tests that need atomic file operations (create temp, rename to final), avoid `QTemporaryFile`; use explicit temp paths and manual cleanup.

## 2026-05-11: MIP/AIP source-file mitigation
- **Discovery:** Every new `.cpp`/`.h` file in this repo may inherit Microsoft Information Protection (MIP) sensitivity labels at rest, causing build tools (`g++`, `head`, `cat`) to see ciphertext (`%TSD-Header-###%...`). The Python interpreter is on the MIP allowlist and reads plaintext.
- **Applied in:** All file creation in Plan A — write new source files via Python's delete-and-rewrite pattern (see CLAUDE.md section "File creation convention"), not via the Write tool. Before any C++ build, run `python tools/decrypt_via_copy.py --apply` to strip labels.
- **Rule:** New `.cpp`/`.h` files must be written via Python. Subagents that produce source code must include the deletion pattern. The decrypt script is idempotent and runs as a build pre-step until labels stabilize.

## 2026-05-11: postgres:16 doesn't bundle pg_cron
- **Discovery:** The official Docker image for `postgres:16` does not include the `pg_cron` extension. Container startup fails on `CREATE EXTENSION pg_cron` with "could not access file pg_cron".
- **Applied in:** `deploy/postgres/Dockerfile` — derived image installs `postgresql-16-cron` from the PostgreSQL Development Group (PGDG) repository before initializing the database.
- **Rule:** When using a postgres Docker image, always derive a custom image for any non-bundled extensions (`pg_cron`, `pg_partman`, etc.). The Dockerfile pattern is: `FROM postgres:16 && apt update && apt install -y postgresql-16-<extension> && ...`.
## 2026-05-28: VBA/COM worksheet copy — capture by name-diff, never by position/ActiveSheet
- **Discovery:** Seeding the post-upload reset snapshots failed two ways that silently corrupted the workbook. (1) `Worksheet.Copy After:=Worksheets(Count)` when the last sheet is **very-hidden** (`_Template_Master`) misplaces the copy, so capturing the new sheet by position grabbed a pre-existing sheet and `snap.Name = ...` renamed it 12 times (only `_Template_11` survived; `_Template_Master` was clobbered). (2) In pywin32, `ws.Copy(After=anchor)` as a **named** arg doesn't bind in late-bound COM and silently spawns a throwaway workbook (0 sheets added to the target).
- **Applied in:** `excel-sidecar/DataViewerUpload.bas` — `AddSnapshotFrom` and `RestoreSheetFromTemplate` copy after/before a **visible** anchor (the "DataViewer Upload" sheet / the live sheet), find the new sheet by **name-diff** (record sheet names before the copy), and never `Delete` the original until the replacement is confirmed present. Recovery COM scripts pass the anchor **positionally** as `Before` (`ws.Copy(beforeSheet)`), not `After=`.
- **Rule:** When copying sheets in VBA/COM: (a) never anchor Before/After on a very-hidden sheet; (b) capture the new sheet by name-diff, not `ActiveSheet` or `Worksheets(Count)`; (c) make any replace transactional — copy first, confirm, then delete; (d) in pywin32 pass `Copy`/`Move` anchors positionally, not as `After=`. Separately: an over-strict guard (snapshot `A1` must equal the live sheet's `A1`) false-skipped a sheet whose template title legitimately differed ("Lifetime Test 2") — prefer a robust structural invariant over brittle equality.

## 2026-05-29: Never reuse a color within a plot
- **Discovery:** Plot palettes were small fixed arrays indexed with `% N`, so colors repeated once the series count exceeded the palette — the Lifetime comparison chart read as "only blue and orange," and 7+ files wrapped hues back to blue. The same `% N` flaw existed in `PlotEngine`, `PlotWidget`, and `RadarChartWidget`.
- **Applied in:** New `AppTheme::seriesColor/seriesColors/shade` (single source of truth, reusing the radar chart's already-vetted no-yellow palette + golden-angle generation past 20). All report charts, GUI plots, and radar overlays route through it; the `ReportGenerator` comparison chart stays grouped by file via distinct base hues + `shade()` per sample.
- **Rule:** Never `palette[i % N]` in a plot — size the palette to the element count via `AppTheme::seriesColors(n)` / `seriesColor(i)` (or `shade()` for grouped charts). No yellow (hue ≈ 45°–70°); keep series saturated and mid-dark — yellow and pale/light colors wash out on projectors.

## 2026-05-29: Repurposing a positional column — audit EVERY consumer, not just the obvious ones
- **Discovery:** Making per-row data-table column index 4 dual-purpose (Resistance double ↔ Puffing Regime string, v2.2.1) required touching far more than the read/write/display path. A non-obvious consumer — the live multi-user conflict "take their value" tooltip (`MainWindow::handleRemoteRowChange`) — used a hardcoded 12-column positional `SELECT ... resistance ...` and stamped values by visual column index, so accepting a remote regime edit silently overwrote the regime with resistance. Per-task reviews missed it (it wasn't in any task's scope); only the whole-feature integration review caught it.
- **Applied in:** `liveColumnForDataCol`/`dataColForLiveColumn` (sheet-aware col↔DB-column map) cover the LiveSync paths; `handleRemoteRowChange` now fetches `puffing_regime` and stamps it into col 4 when `sheet->hasPerRowRegime`. `DataRow` keeps BOTH `resistance` and `puffingRegime`; the per-sheet `SheetResult::hasPerRowRegime` flag drives all branches.
- **Rule:** When a positional column/index changes meaning, grep the WHOLE repo for EVERY positional consumer of that index/field/DB-column (SELECT column-lists, `value(N)`, index-based stamps, write-back arithmetic, conflict/tooltip paths), not just the obvious populate/edit/save. A final cross-task integration review is where these between-the-cracks consumers surface — do it.

## 2026-06-05: A spec-conformance audit can't catch a spec that doesn't match intent
- **Mistake:** Plan C (auto-recovery) was brainstormed, built, audited (5 parallel auditors), and shipped as v2.3.0 scoped as **crash-only** recovery — it deliberately cleared the snapshot on a clean/declined close and only offered to restore after a crash/update. The user's very first real test ("opened files, closed, said *don't save*, then nothing to reload") exposed that they actually wanted **restore-my-last-session**: persist the snapshot across *any* close and auto-offer to reopen (files + unsaved edits) on *every* launch. The deep audit passed because it verified the code against the (mis-scoped) spec — conformance ≠ correctness of intent.
- **Root cause:** Brainstorming locked "clear on clean close" + "crash detection" as decisions without surfacing the one UX fork that actually mattered: *does a normal/declined close discard the session, or should it always be restorable next launch?* That question was never put to the user.
- **Applied in:** v2.3.1 — `closeEvent` finalizes via `flushNow(true)` instead of `clear()`; the launch prompt auto-offers on any prior session and **lists the item names**; restore includes unsaved edits; DB-loaded files are snapshotted; "No" keeps the session retrievable (no accidental-dismiss data loss).
- **Rule:** For any "don't lose my work" / recovery / session-restore feature, explicitly ask the user the close-behavior fork up front (clean/declined close = discard vs. always-restorable?). And never treat a passing spec-audit as proof the feature is right — for user-facing behavior, verify against the user's actual goal with a quick real run (or have them try it) *before* calling it done, because an audit only proves the code matches the spec, not that the spec matches what they wanted.

## 2026-05-29: Ephemeral test Postgres applies init.sql's base block only — not migrations
- **Discovery:** `tests/start-test-postgres.ps1` applies only the `BEGIN..COMMIT` block of `init.sql`, NOT the files in `deploy/postgres/migrations/`. So DB tests that exercise migration-only schema (e.g. sensory header presets from `2026-05-20-sensory-header-presets.sql`) FAIL against the ephemeral container (`saveSensoryHeaderPresets`/`saveSensoryLayout` return FALSE) — a pre-existing, environmental failure unrelated to whatever feature is under test.
- **Applied in:** The v2.2.1 `data_rows.puffing_regime` column was added to BOTH `init.sql` (base block) AND a migration file — so the ephemeral container has the column and `perRowRegime_roundTrip_newAndOld` passes. The migration is only for already-deployed DBs.
- **Rule:** A new column/table must go in `init.sql`'s `BEGIN..COMMIT` block (fresh installs + the test container both read it), with a separate migration file ONLY for upgrading deployed DBs. When triaging `tst_databasemanager` failures against the local container, first check whether the failing feature's schema lives only in a migration.

## 2026-06-10: A sync heuristic must never DISCARD a save (v2.4.0 data-loss postmortem)
- **Mistake:** Three v2.4.0 mechanisms each assumed "LiveSync already delivered every edit to the DB": (1) `VersionMismatch/RowDeleted => skipped -- already up to date via LiveSync` dropped the dirty flag without writing; (2) the DB-authoritative score merge unconditionally took DB values for score cells; (3) flushNowAndWait()'s timeout was unchecked. When LiveSync was gapped (id<=0 sessions never stream; worker connection broken with 26000 errors and no reconnect), each mechanism actively destroyed the user's in-memory edits -- production log showed 23 silent save-discards in 3 days ("file reverted the next day").
- **Correction (v2.4.1):** fresh-version OCC inside the write cores (row-level last-writer-wins by design); callers retry/reinsert and NEVER clear dirty on failure; panels track dirty cells and the merge keeps in-memory values for cells the user touched; worker reconnects; failures surface in the sync indicator.
- **Rule:** Any "skip this write, another component already did it" heuristic must VERIFY, not assume. Cross-component freshness assumptions need arbitration data (dirty set, timestamps, versions). A save path may fail loudly or retry -- it may never silently drop user data.

## 2026-06-10: jsonb cell streaming must preserve types (the real "reset to 5")
- **Discovery:** `dve_commit_cell_json` stored every streamed value as `to_jsonb($2::text)` -- numeric scores landed as JSON *strings*. `QJsonValue::toDouble(5.0)` returns the DEFAULT for strings, so every live-streamed score read back as 5.0 on the next fresh load. This had corrupted rows since v2.0.2 and was invisible to tests because the test helper simulated commits with `::double precision` (a number) instead of the production text path.
- **Correction:** numeric-regex CASE in the stored function (numbers stored as numbers), tolerant `jsonToDouble` reader (repairs historical string rows on read), ensureSchema CREATE-OR-REPLACE heal. Also: CREATE OR REPLACE with a different arity creates an OVERLOAD, not a replacement -- the live DB had both a 6-arg and 7-arg `dve_commit_cell_json`; only pg_get_functiondef/pronargs reveals which one the app actually calls.
- **Rule:** Test helpers must replicate the production write path byte-for-byte (same stored fn, same casts). When healing stored functions, match the exact arity the client binds, and check for overload shadows.

## 2026-06-10: Qt Test totals shrinking == stale binary, not lost tests
- **Discovery:** Suite totals regressed (64->63, 17->15) across verification runs. Cause: the test runner writes per-suite logs to a fixed `%TEMP%\<suite>.txt`, and polling mid-build reads the PREVIOUS run's file; separately, a build that fails/lags for one suite leaves an old exe that runs happily with old counts.
- **Rule:** Trust only totals from a log you watched get written: run the freshly-built suite exe directly with `-o <file>,txt`, or verify the exe mtime postdates your build. Before concluding tests were lost, grep the source for the test names.

## 2026-06-10: Never hard-block the user; auto-resolve or offer options (product directive)
- **Directive (user, verbatim intent):** "I don't want to stop the user experience in their tracks at any point, just provide guidance and ALWAYS provide options." Applied: duplicate/renamed session names auto-suffix `_1/_2/_3` silently (status-bar notice, no modal); closing an unnamed session offers Name It Now / Discard Session / Cancel instead of a forced-naming OK box; TPM close-persist failure offers Retry / Close Anyway / Cancel; TPM re-adds of the same file mint a new timestamped DB version instead of overwriting.
- **Rule:** For any new validation/conflict surface in this app: first try silent self-resolution (suffix, version, merge); if user input is genuinely required, a dialog must offer at least [do it for me] / [destructive-but-explicit] / [cancel] -- an OK-only blocker is a design bug.

## 2026-06-18: Database Browser opens from the Home ribbon, not Tools (SP4-T3 visual loop)
- **Mistake:** Told the user to open the Database Browser via "Tools -> Database Browser". It is the "Database" large button in the **Database group on the Home ribbon** (`MainWindow.cpp:641`: `dbBtn` -> `onOpenDatabaseBrowser` -> `DatabaseBrowserDialog`). Has been on Home since v2.

## 2026-06-18: Running the bare build for a visual check needs windeployqt + libpq + resources (SP4-T3 visual loop)
- **Discovery:** `build\release\DataViewer.exe` is the raw linker output -- no Qt runtime DLLs (Qt6Sql.dll missing -> "code execution cannot proceed"), and `resourcePath()` finds no `resources/` so ribbon icons render blank. `windeployqt` deploys Qt's own DLLs/plugins but NOT the app's `resources/` PNGs (the Inno installer does that), and the QPSQL driver needs `vendor/libpq-16/*.dll` beside the exe.
- **Rule:** To run the freshly-built exe for a visual check WITHOUT reinstalling: `windeployqt --release --compiler-runtime build\release\DataViewer.exe` + `cp vendor/libpq-16/*.dll build/release/` + `cp -r resources build/release/resources`, then launch with `LOCALAPPDATA` pointed at a sandbox `db.conf` (test container, never prod). Blank icons / missing DLLs in such a run are deployment artifacts, NOT regressions -- they do not ship.

## 2026-06-23: A "file open" bug has THREE entry points -- repro the exact one before fixing
- **Mistake:** "Opening an already-open file creates a `_1` duplicate that splits the DB." I assumed the TPM path (`MainWindow::routeFile`->`loadFile`->`m_loadedFiles`) and fixed only that (v2.4.11). The owner's actual repro was a **sensory** file, which routes to `SensoryPanel::loadFile` (a separate `m_sessions` list with no dedup) -- so the duplicate persisted. The `dataviewer.log` even showed the sensory-specific signal (`tryWriteSensorySessionAutoSuffix ... "New test sensory_1"`) which I had dismissed earlier as "a separate intended thing."
- **Correction:** There are THREE file-open paths, each with its own session list + dedup: TPM (`routeFile`->`loadFile`->`m_loadedFiles`, keyed by normalized file path), Sensory (`SensoryPanel::loadFile`->`m_sessions`), Detailed (`DetailedSensoryPanel::loadFile`->`m_sessions`). Sensory/detailed dedup by the DB natural key (`session_name`+`tester`+`date`), NOT by `sourceFilePath` (which exists on the struct but is never set and isn't persisted across the recovery/DB JSON round-trip, so recovered sessions carry none). Fixed all three (v2.4.11 TPM, v2.4.12 sensory+detailed).
- **Rule:** For a UI bug with multiple entry points (file types, modes, panels), enumerate them and confirm WHICH the user hit -- the on-screen panel + the log signals tell you -- before coding a fix; don't assume the first path. And don't dismiss a concrete log signal (the `_1` was sensory) as unrelated.
- **Follow-up (cost me 4 build cycles):** "open a file" actually meant "load a session from the DATABASE BROWSER" -- a 4th entry point (`SensoryPanel::loadSessions`, NOT loadFile). I only found it by reading `dataviewer.log` and noticing my `[sensory-load]` diagnostic NEVER fired (= the function I kept fixing wasn't even being called). **Meta-rule: after a fix fails to work, do NOT rebuild another guess. Instrument, have the user reproduce, and READ THE LOG / ask for the exact UI action to confirm the code path is actually executed before iterating again.** A `git grep` for every caller of the relevant panel method (`loadSessions`, `loadFile`, `newSession`, recovery restore) up front would have surfaced all entry points at once. (DB loads are best deduped by row `id`, the reliable identity -- not file path or natural key.)
- **Closing (v2.4.15):** Owner then made it a standing rule: *"always cover every path when I'm describing loading -- assume all paths and check each one"* (saved as the `cover-every-load-path` memory). Applied it PROACTIVELY and found the SAME dedup gap in two more entry points: `SensoryPanel::loadFiles` (the multi-select "Load Sensory Files" button + its Excel/JSON helpers) and `DetailedSensoryPanel::loadFiles` -- both blindly appended. Fixed both and consolidated the sensory dedup into one shared `reconcileNewlyLoaded(firstNew)` helper so `loadFile`/`loadFiles`/`loadSessions` can't drift apart again (the root cause of this whole saga was exactly that drift). The full set, now all deduped: TPM `routeFile`; sensory `loadFile` / `loadFiles` / `loadSessions`; detailed `loadFile` / `loadFiles` (detailed `loadSessions` REPLACES the list, so it structurally can't dup).

## 2026-06-23: Show the progress bar from the START of a blocking op, not partway
- **Bug (owner):** Close -> "Save All" after an edit froze the window for ~2s with no indicator, THEN the snapshot "Saving offline copy..." bar appeared for the rest. The dead gap was the DB save (`onUpdateDatabase`) inside `promptSaveDatabase`, which ran with NO dialog; only the later `regenerateSnapshotWithProgress` showed a bar.
- **Fix (v2.4.16):** one member `QProgressDialog* m_closeProgress` created at the START of the Save-All work (`makeBusyDialog`, busy/indeterminate), updated as it saves, and REUSED by `regenerateSnapshotWithProgress` (switched to determinate) so close shows ONE continuous bar; `closeEvent` tears it down via `closeProgressEnd()`. Audited the other blocking ops -- file load, report gen, snapshot refresh, DB repair already show live bars (status strip or modal dialog), so they were left as-is. Did NOT bolt a modal onto report gen: each report emits `reportFinished` -> `onReportFinished` pops its own modal box (per file in multi-file), which a second modal would fight.
- **Rule (owner directive; memory `progress-bars-for-blocking-ops`):** any operation that blocks the UI must show a progress indicator from the first heavy step -- never a frozen window before the bar. Construct + `show()` the dialog and `processEvents(ExcludeUserInputEvents)` BEFORE the work, not after phase one. A wait cursor is NOT a substitute for a hard-blocking op (it won't paint without an event pump, and pumping inside a deliberately-synchronous drain like `finishExcelWritesBlocking` risks re-dispatching the very async work it's draining).

## 2026-06-24: QDockWidget — maxWidth blocks re-docking; objectName required to persist
- **Bug (owner, v2.5.3):** After popping the Notes/Navigator docks out (floating), neither could be re-docked (drag-to-edge or the dock button did nothing); and the Navigator never remembered its float/position across runs while the Notes dock did.
- **Root cause 1 — re-dock:** a `setMaximumWidth()` (we capped both docks at 320) on a `QDockWidget` prevents `QMainWindow` from re-docking it after float — the dock-area layout can't create the placeholder drop-gap for a max-constrained widget, so the drop is silently rejected. A *minimum* width does NOT cause this; only a maximum does.
- **Root cause 2 — persistence:** `QMainWindow::saveState()`/`restoreState()` key docks by `objectName` and **silently skip** (with a runtime warning) any dock lacking one. Navigator had no `objectName`; Notes had `"notesDock"`.
- **Fix (v2.5.4):** removed the `setMaximumWidth` caps (control width via `resizeDocks()` / `restoreState()` instead; compact mode still uses a 32px max to collapse the icon strip, which is fine since re-dock isn't a use case there), and gave the Navigator `setObjectName("navigatorDock")`. When a dock gains/changes an objectName, old saved layouts can't match it — re-balance once (bump a QSettings flag) so the user sees a clean default, then their sizing persists.
- **Rule:** Never use `setMaximumWidth/Height` to size a floatable `QDockWidget` — it breaks re-docking; use `resizeDocks()`. Every dock that should persist MUST have a unique `setObjectName` set BEFORE `restoreState()` runs. When changing a dock's objectName, treat saved layouts as stale and re-apply a default once.
