# v2.10 Master Spec - North Star

This document is the single north star for the v2.10 sprint.
It is a living document: at the end of every phase it is updated with any deviations from this plan, so it always reflects the true state of the work (see the Phase Log at the end).
Each phase gets its own detailed implementation plan; this spec defines what those plans must deliver and the bar they must clear.

## 0. Sprint cadence (owner-chosen, applies to every phase)

Each phase runs the same loop, and a fresh session can pick up at any step:

1. **Review this master spec** - re-read it in full, especially the Phase Log, before doing anything.
2. **Brainstorm + plan** - run the brainstorming skill for the phase's design decisions (with the owner), then the writing-plans skill to produce `docs/superpowers/plans/2026-MM-DD-v2.10-phaseN-<topic>-plan.md`.
3. **Execute** - implement the plan (TDD, subagent-driven or inline per plan), clear the exit gate in Section 6.
4. **Update this master spec** - append the phase's outcome and any deviations to the Phase Log, correct the sections above if reality diverged.

The Phase 1 plan is produced in the same session as this spec (steps 1-2 done together): `docs/superpowers/plans/2026-07-16-v2.10-phase1-multiuser-edit-integrity-plan.md`.
Phases 2-4 start at step 1.

## 1. Vision

Fix the sprint's one urgent defect - multi-user sensory sessions silently reverting each other's edits - at its root, with the care the save path demands (the v2.4.x regressions are the cautionary tale), then ship two quality-of-life plot features, wrapped in a single deployable desktop release v2.10.0.
The overriding requirement is zero regressions on the save/sync path: Phase 1 is repro-first and TDD-mandatory, and every phase leaves the full suite green and the build `-Werror` clean before the next begins.

### Phase 1 - Multi-user edit integrity (DV-25 + DV-28)

Goal: a committed edit in a co-open sensory or detailed-sensory session can never be reverted by another client's (or this client's) stale whole-session save, and an unchanged session is never written at all.

The bug, precisely (root-caused during triage, code-verified):

- Client A's sample-name edit commits to the DB per-cell via LiveSync (`SensoryPanel.cpp:496` -> `commitCell`).
- Client B's `MainWindow::onUpdateDatabase` (`src/MainWindow.cpp:5076`) re-saves EVERY open sensory session unconditionally on each autosave tick / Ctrl+U / close - there is no per-session dirty check (the TPM loop at `:5049` filters on `m_modifiedFilePaths`; the sensory and detailed loops have no equivalent).
- The whole-session write is a read-merge-write (`tryWriteSensoryCore`, `src/database/DatabaseManager.cpp:1753`) that starts from B's IN-MEMORY JSON and overlays DB values only for the 5 score metrics (`mergeSensoryPreservingDbScores`, `src/pipeline/SensoryData.cpp:111`; dirty-cell recording at `SensoryPanel.cpp:948-957` gates on `kSensoryMetrics`).
- So every non-score per-sample field - name, comments, voltage, resistance, heating technology, power type, puff length - is silently reverted to B's stale copy.
  Scores were protected by the v2.5.0 RC2 dirty-cell work; nothing else was.
  That is why only names were noticed (DV-25's "may apply to other edits" is correct).
- The detailed-sensory twin has the same shape (`mergeDetailedSensoryPreservingDbScores`, `DatabaseManager.cpp:2389`, loop at `MainWindow.cpp:5185`).

Owner decisions (2026-07-16): fix BOTH panels; protect ALL per-cell sample fields (not just name/comments).

Design - repro first, then two independent layers:

- **Layer 0 - E2E repro (red before any fix).**
  Headless two-client test against the test Postgres container: "client B" loads a session into a stale in-memory struct, "client A" commits `samples[0].name` via the per-cell path, B runs the whole-session save, assert the DB name reverted.
  Twin test for detailed sensory.
  This failing test is what both layers must turn green.
- **Layer 1 - DV-28, per-session dirty gate.**
  A `dirty` flag on `SensorySession` / `DetailedSensorySession`: set by any local edit (card edits, header edits, add/remove sample, imports), cleared on successful save.
  Remote applies cannot set it (they run under `QSignalBlocker`); programmatic loads (`fromSample`) do not fire commits.
  The save loops skip sessions with `id > 0 && !dirty && dirtyCells.isEmpty()`; never-persisted (`id <= 0`) and rename-forced sessions always save.
  The gate applies to autosave, Ctrl+U, and close alike - safe because Layer 2 is the correctness backstop.
- **Layer 2 - DV-25, full merge coverage.**
  One shared per-sample field list (the 5 scores + name, comments, voltage, resistance, heating_technology, power_type, puff_length_sec).
  `dirtyCells` recording extends from scores-only to that full list; both merge functions arbitrate the full list in BOTH regimes (index-aligned and uid-keyed): **DB-authoritative unless locally dirty**.
  This flips non-score fields from "local always wins" to "DB wins unless I touched it" - the semantics scores already have.

Main risk + mitigation:

- Layer 2's flip means a local edit that fails to register as dirty would be reverted by this client's OWN save - a data-loss shape.
  Mitigation: dirty recording rides `SampleCard::cellCommitted`, which already fires for every field in the list (`SensoryPanel.cpp:335-502`); the plan carries a per-field TDD matrix including the LiveSync-down case (the RC2 scenario, extended to every field).
- The dirty gate could skip a session whose edit path forgot to set the flag.
  Mitigation: the flag is set at the same choke points that already mark the store-level `m_sensorySessionsDirty`; the plan enumerates every edit entry point (cover-every-path rule).

Acceptance:

- The two-client repro test proves the revert is fixed for name + comments + one non-score field, in both panels (red -> green demonstrated).
- An unchanged open session's autosave issues NO UPDATE at all - asserted via the `pg_stat_user_tables.n_tup_upd` delta, which still counts UPDATEs whose bump the DV-23 trigger suppressed.
- With LiveSync down, a local edit to each field in the list still persists via the whole-session save (no regression of the RC2 protection).
- Full suite green, `-Werror` clean.
- Owner two-machine smoke test: a rename sticks with two clients co-open (and a stale co-open client's autosave no longer reverts it) before the Plane issues move to Ready for Release.

### Phase 2 - Sensory annotated Save Plot (DV-27)

Goal: the sensory-mode Save Plot export appends the per-sample notes below the chart image - one blocked-out section per selected sample ("Sample x - <note>"), ~8pt, tight margins, zero overlap, covering multi-select and the test-averages view.

Anchors (design decisions belong to the Phase 2 brainstorm):

- Current export renders the bare chart: `SensoryPanel::onSaveChart` (`src/ui/SensoryPanel.cpp:1692`).
- Reuse/mirror DV-22's TPM machinery: `PlotEngine::composeAnnotatedExport` (`src/plotting/PlotEngine.cpp:984`) - this variant is simpler (a block list below the plot, no arrow/leader geometry).
- Notes source: the per-sample comments field (committed as `comments`).
- v2.8 lesson: expect owner smoke-fix rounds on visual polish; build the offscreen preview harness early (the DV-22 `_plotprobe` pattern).

Acceptance sketch (to be firmed in the Phase 2 plan): exported image = chart + notes strip, block count == selected samples with notes, no overlapping text at any note length (wrap + grow image height), no-notes export unchanged, closed-loop PNG probe.

### Phase 3 - Name-pinned plot colors (DV-26)

Goal: the same sample name renders in the same color everywhere it appears - sensory, TPM, and generated reports (owner-scoped 2026-07-16 to all three).

Anchors (design decisions belong to the Phase 3 brainstorm):

- All plot paths assign colors positionally today: `RadarChartWidget.cpp:359-609`, `PlotWidget.cpp:599-762`, `ReportGenerator.cpp:112`/`:750`, `PlotEngine.cpp:500`/`:1232`.
- The fix is a stable name -> palette-index mapping layer over `AppTheme::seriesColor`, NOT hash-to-color (hashing can collide/repeat, violating the never-reuse-a-color rule).
- Open design questions for the brainstorm: the mapping's scope and lifetime (per loaded working set vs persisted), collision policy when the name union exceeds the curated palette, and whether per-file shading (`AppTheme::shade`) interacts.

Acceptance sketch: two files with overlapping sample names show identical colors per name across panels and in report images; all colors in any single plot remain distinct; `--ui-stress` + PNG probes pass.

## 5. Engineering guardrails

Hard constraints for every phase, carried from the v2.8 spec plus this sprint's specifics.

Branch and workflow:

- All work on `feature/v2.10`, branched from `main` @ `130c90a`.
- This is the work machine (S1134987): develop, build, self-test here; the owner eyeball-tests installed builds; the owner alone touches Synology/NAS.
- Never kill or attach to the user's running Excel; the repo is public - no committed secrets; no agent co-author on commits; plain dashes, never em dashes, in authored text.
- Token efficiency: verify inline, no big agent fan-outs, cap any workflow at ~10-15 agents.

Build and test gates (per phase, before the phase closes):

- `python tools/decrypt_via_copy.py --apply` before any C++ build (MIP re-encrypts source at rest).
- Rebuild in-tree at the repo root, not only in `build/`.
- Full test suite green with `DVE_TEST_PG_CONN` + `vendor\libpq-16` on PATH + the `dve-test-pg` container (it must have `deploy/postgres/migrations/` applied - `start-test-postgres.ps1` auto-applies); if Docker is off, ask the owner to start it.
- Build `-Werror -Wall -Wextra` clean.

Save-path rules (Phase 1 especially):

- Repro before fix; TDD with the failing test demonstrated red -> green; never weaken the RC1/RC2/RC4 protections documented in the v2.4.x history (`docs/superpowers/specs/2026-06-10-v24-save-sync-regressions-evidence.md`).
- Fire-and-forget QoL writes go through `DatabaseManager::runIsolatedWrite`, never the shared connection.
- Every load/save behavior has multiple entry points (TPM vs sensory vs detailed, crossed with file-open / multi-file / DB-browser / recovery / autosave / Ctrl+U / close); enumerate and cover all of them.

UI/visual gates (Phases 2-3):

- `--ui-stress` screenshot harness on any UI change; a dedicated closed-loop PNG probe per visual feature.
- Never reuse a color within a single plot; no yellow; size palettes to element count.
- No cut-off text at any window size; progress indicator from the START of any UI-blocking operation.
- Per-mode ribbon button sets keep identical count/order/positions (if any ribbon change happens).

## 6. Phase exit gate

A phase is done only when all of the following hold:

1. Every acceptance criterion for the phase's items is met and demonstrated.
2. New tests exist for each change and the full suite is green.
3. The build is `-Werror` clean.
4. For UI phases, `--ui-stress` and the feature's PNG probe pass.
5. An internal installer (v2.9.x, patch bumped from the previous test build) is built and the owner has smoke-tested it.
6. The Plane issues for the phase are moved to Ready for Release (owner promotes to Done at release).
7. This master spec's Phase Log is updated with any deviations.
