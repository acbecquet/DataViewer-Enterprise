# v2.8 Master Spec - North Star

This document is the single north star for the v2.8 sprint.
It is a living document: at the end of every phase it is updated with any deviations from this plan, so it always reflects the true state of the work (see the Phase Log at the end).
Each phase gets its own detailed implementation plan; this spec defines what those plans must deliver and the bar they must clear.

## 1. Vision

Close out the v2.7 carryover and the new bug-form requests as a sequence of small, independently verifiable phases, shipped in two deployable releases.
The overriding requirement, stated twice by the owner, is zero regressions and robust behavior.
Every phase leaves the full test suite green, the build `-Werror` clean, and - for any UI work - closed-loop screenshot/PNG probes passing, before the next phase begins.
Value ships early: the smallest, lowest-risk items go first so the build-and-release loop is exercised before the large features land.

## 3. Release plan

Two deployable releases, packaged by subsystem.

| Release | Phases | Contents | Deploy mechanic |
|---------|--------|----------|-----------------|
| v2.8 | 1, 2 | Quick wins + TPM plot/notes | Desktop installer, owner drops on Synology |
| v2.9 | 3, 4 | Mobile form + NOTIFY-storm fix | See note below |

Deploy-mechanic note for v2.9:
DV-21 (Phase 3) is a NAS web-form deploy under `deploy/sensory-collect`, not the Windows installer.
The owner deploys the web form to the NAS; the agent never touches the NAS or Synology.
DV-23's desktop-side fix rides the v2.9 desktop installer.
So "v2.9" is really the second desktop installer plus an independent NAS web-form update.

The internal-patch versioning convention still holds: patch `z` builds are internal and not deployed; the minor `y` is the deployable unit.
Concretely, during the v2.8 sprint the internal test installers are versioned v2.7.1, v2.7.2, ... v2.7.x; only the final deployable build is bumped to v2.8.0.
Likewise the v2.9 sprint's internal builds are v2.8.1 ... v2.8.x, wrapping to v2.9.0 at release.
Do not stamp an internal test build with the target minor (v2.8.x / v2.9.x); that number is reserved for the deployable wrap.

### Phase 2 - TPM plot + notes (v2.8)

Goal: deliver the two plot/notes features together because they share the same plumbing (the PlotEngine axis-to-pixel transform, the PlotWidget geometry, and the notes model).

- DV-18: make the rendered plot image clickable; a click near a data point finds the nearest note row and scrolls to + highlights its note card.
  This is the reverse direction of the v1 note-card -> plot-point highlight (`PlotWidget::selectPuff`), which already shipped.
- DV-22: upgrade the TPM Save-plot button so the export is an annotated figure.

DV-22 confirmed design:

- TPM mode only; a plot with no notes exports the plain plot unchanged.
- A notes header band sits above the plot, one 6 pt row per (sample, puff-with-note), sorted by puff then sample, formatted like the Notes Story panel: `Sample - puff # - current TPM (avg TPM) - note text`.
- The plot itself carries only thin amber vertical lines with a small downward arrowhead at each noted puff; no rings/circles.
  Amber is deliberate so the note-lines never blend into the red Maxcore data series.
- The exported image height auto-grows with the number of note rows.

Key files:

- DV-18: `src/plotting/PlotWidget.cpp` (add `mousePressEvent` + inverse pixel-to-data mapping), and `src/plotting/PlotEngine` must expose its plot rect + x/y data ranges so the click can be inverse-mapped.
- DV-22: `PlotWidget::onSaveImage()` at `src/plotting/PlotWidget.cpp:389` (save path), `src/plotting/PlotEngine.cpp` (reuse the note-row -> (puff, tpm) mapping, but draw only the thin lines for the export), and the NotesStoryPanel note model for the header rows.
  Compose the header + plot into one QImage in the save path.

Acceptance:

- Clicking near a plotted point scrolls to and highlights the correct note card; clicking empty space does nothing.
- Save-plot with notes produces a taller PNG with a legible 6 pt header and thin amber arrowed lines at exactly the noted puffs.
- Save-plot with no notes produces the plain plot, visually identical to the current plain export.
- A closed-loop render-to-PNG probe asserts header row count equals note count and line count equals the number of distinct noted puffs.

### Phase 4 - NOTIFY storm (v2.9)

Goal: root-cause and stop the periodic self-update churn on `sensory_sessions`, then guard against its class.

- DV-23: an unidentified client updates `sensory_sessions` id=1418 about once per second, producing a continuous NOTIFY stream that amplified the v2.7 relayout freeze.

Investigation-first: identify the client and whether the write even changes data (a no-op UPDATE that still bumps `updated_at` and fires NOTIFY).
Likely areas: the LiveSync write + NOTIFY path (`src/database/LiveSync.cpp` / `LiveSyncWorker.cpp`), presence/heartbeat timers, the phone-form append (`deploy/sensory-collect/app.py`, `dve_append_sensory_sample`), and the OCC `updated_at` bump; cross-check `2026-06-11-notify-maintenance-suppression.sql`.

Acceptance:

- With the app idle and one session open, `sensory_sessions` receives no periodic self-updates.
- NOTIFY fires only on genuine edits.
- A test covers the "no-op save does not NOTIFY" contract.
- Data hygiene noted in the handoff (delete the junk `format_a.xlsx` DB row, fileId 242) is tracked separately, not part of this fix.

## 5. Engineering guardrails

These are hard constraints for every phase, distilled from the v2.7 retro and the project rules.

Branch and workflow:

- All work on `feature/v2.8`, branched from `main`.
- This is the work machine (S1134987): develop, build, and run the deployment self-test here; the owner eyeballs the installed build, then the owner alone drops the installer on Synology.
- Never touch anything under `SynologyDrive`; never kill or attach to the user's running Excel (`DispatchEx` only); the repo is public, so no committed secrets; no agent co-author on commits; plain dashes, never em dashes, in authored text.

Build and test gates (per phase, before the phase closes):

- Run `python tools/decrypt_via_copy.py --apply` before any C++ build (MIP re-encrypts source at rest).
- Rebuild in-tree at the repo root, not only in `build/`: the installer packages the root `release/` tree, and a build-dir-only rebuild once shipped a no-op installer.
  The `build_installer.bat` staleness gate must stay.
- Full test suite green (52 suites) with `DVE_TEST_PG_CONN` + `vendor\libpq-16` on PATH + the `dve-test-pg` container; if Docker is off, ask the owner to start it.
- Build `-Werror -Wall -Wextra` clean; fix the underlying code rather than downgrading warnings.

UI/visual gates (Phases 1-2 especially):

- Run the `--ui-stress` 28-case screenshot harness on any UI change.
- Build a dedicated closed-loop PNG probe for each visual feature (the DV-22 annotated export and the DV-20 radar), because scrollbar metrics and version strings cannot catch visual regressions.
- Standing plot rules: x runs 0..(last point + 1), y is anchored at 0 and tops out at (max + 1); no per-chart floors; no datapoint ever clipped.
- No cut-off text at any window size: scroll to the end (ElideNone + content-sized column + per-pixel scroll) plus tooltips; wrapping is only safe in a QTableWidget or a QLabel, never via viewport-width-dependent item-view size hints.

Correctness guardrails:

- Every "load/open" behavior has multiple entry points (TPM vs sensory vs detailed, each crossed with file-open / multi-file / DB-browser / recovery); check all of them.
- A single shared flag must be derived from the max/union over all views it drives.

## 6. Phase exit gate

A phase is done only when all of the following hold:

1. Every acceptance criterion for the phase's items is met and demonstrated.
2. New tests exist for each change and the full suite is green.
3. The build is `-Werror` clean.
4. For UI phases, `--ui-stress` and the feature's PNG probe pass.
5. The Plane issues for the phase are moved to Ready for Release (owner promotes to Done at release).
6. This master spec's Phase Log is updated with any deviations.
