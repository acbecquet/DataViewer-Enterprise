## 4. Learnings

- **DV-23 root cause (the ~1/sec sensory_sessions writes):** `MainWindow::onUpdateDatabase`
  (`src/MainWindow.cpp:5076`) re-saves EVERY open sensory session **unconditionally** - there is
  no per-session dirty check. Contrast the TPM loop directly above it (`src/MainWindow.cpp:5056`),
  which only writes files in `m_modifiedFilePaths`. So each unchanged session (e.g. id=1418) got a
  no-op UPDATE -> version bump + `updated_at` + NOTIFY on every autosave tick. This is exactly the
  ticket's "no-op UPDATE that still bumps updated_at and fires NOTIFY".
- **Ruled out (each verified in code, not assumed):** the DV-13 stopwatch (`src/ui/SensoryPanel.cpp:446`
  tick timer sets button text only; commits once on Stop), the remote-cell handler
  (`SensoryPanel::onRemoteCellChanged` applies under a `QSignalBlocker`), the self-NOTIFY loop
  (`src/MainWindow.cpp:331` filters `c.updatedBy == selfUuid`), all timers <5s.
- **Rate caveat:** the autosave is a 5s single-shot DEBOUNCE (`src/MainWindow.cpp:506`), so it alone
  writes one row ~0.2/sec; the reported ~1/sec was a rough estimate or amplified by the (since-fixed)
  v2.7 relayout thrash re-firing widget `valueChanged` -> spurious per-cell `commitCell`. Not
  reproducible (offending client gone since 2026-07-08).
- **Why not fixed:** the shipped DB guard already makes those no-op writes harmless, and the save
  path is data-loss-prone (see the v2.4.x save-regression history / `v2-4-1-regression-fix-batch`
  memory). A change-detection check there is a genuine data-loss risk for a now-neutralized
  inefficiency. Deferred to a Plane ticket (see Action Items).
- **Sensory persistence model:** sensory edits are persisted per-cell via LiveSync
  (`SensoryPanel` -> `commitCell("sensory_sessions", ...)`); `onUpdateDatabase` is only the
  whole-session fallback for Ctrl+U + on-close (`src/MainWindow.cpp:4175-4179`). Editing a TPM file
  re-arms the shared 5s `m_dbSaveTimer`, which then also re-saves all sensory sessions.
- **DB deploy is a pure server-side change:** the trigger fix runs in Postgres, so every existing
  desktop install benefits with no update. `ensureSchema` (`src/database/DatabaseManager.cpp:464`)
  only heals `notify_row_change` and keys off the `dve.maintenance` marker - it will NOT revert this
  fix, but also cannot deliver the paired `bump_version` change, which is why the migration is the
  delivery path.
- **Versioning rule (confirmed this sprint):** a service-only sprint (web/DB, no C++) does NOT bump
  the desktop version. See the `feedback_sprint_by_minor_version` memory.
