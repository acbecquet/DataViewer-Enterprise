## What to do next — Plan B Phase 3 (the big one)

Phase 3 is the **DatabaseManager refactor**. It is the single most invasive task in the entire initiative. Do NOT attempt it casually.

### What Phase 3 changes

- `src/database/DatabaseManager.h`/`.cpp` (1786 lines) — currently SQLite-backed. Rewires internals to use `PostgresConnection`. Public method signatures STAY the same so all callers in MainWindow keep compiling.
- Introduces a new `WriteResult` enum (`Success`, `VersionMismatch`, `RowDeleted`, `UniqueViolation`, `OfflineReadOnly`, `OtherError`).
- Modifies save methods to return `WriteResult` instead of `bool`. Add a `bool` overload that maps non-Success to false for incremental migration.
- Adds optimistic-concurrency `WHERE id = ? AND version = ?` to every UPDATE.
- Rewrites `tst_databasemanager` (24 tests, currently SQLite-based) to target Postgres backend + add conflict tests.

### Why it's hard

- 1786 lines of intricate SQLite-specific logic (lastInsertId, BLOB binding, JSON-as-TEXT, the cross-machine lock code that's still in there from before).
- The build is broken until the refactor is COMPLETE. Cannot ship a partial Phase 3 — every method must be migrated together.
- Hierarchical save (file → tests → samples → data_rows → images) involves nested loops with foreign-key relationships. Each layer needs the parent's `RETURNING id` to thread through.
- The existing tests in `tst_databasemanager` cover edge cases worth preserving — read them first to understand the contract.
- `MainWindow` has ~50 call sites that depend on `DatabaseManager`'s current signatures. If those signatures change, all sites need updates simultaneously.

### Recommended approach for Phase 3

1. **Don't dispatch a single mega-subagent.** Break Phase 3 into 4 sub-batches:
   - **3a.** Replace `m_db` (QSqlDatabase) with `m_pg` (PostgresConnection) in the constructor + `open()`/`close()`. Add a build-passing skeleton where every method returns false. Get the main app linking again.
   - **3b.** Reimplement `saveFile` + `loadFile` + `loadFileByPath` + `listFiles` + `removeFile` against Postgres. Run the relevant subset of `tst_databasemanager`.
   - **3c.** Reimplement sensory + detailed sensory + settings methods.
   - **3d.** Add `WriteResult` enum, retrofit existing methods to return it, add the version-check UPDATE pattern. Update tests to exercise the conflict paths.

2. **Read the existing `DatabaseManager.cpp` end-to-end before touching it.** Several methods do non-obvious things (e.g., the natural-key upsert for sensory sessions, the dedup migration in `initSchema`). Don't lose those.

3. **Test incrementally with a fresh Postgres container.** `tests/start-test-postgres.ps1` is your friend. Wipe between runs.

4. **The lock-file code is still in `DatabaseManager.cpp`** (`writeLockFile`, `readLockFile`, `pathLooksCloudSynced`, `LockInfo`, `forceReleaseLock`, `m_lockPath`, `m_lockInfo`). Plan C explicitly deletes it. You can either delete in Phase 3 (cleaner) or leave for Plan C (less to think about). The spec assumed Plan C would do it; pragmatically Phase 3 is the natural place.

5. **MainWindow side: the spec promised "public signatures stay the same."** Honor that. If you have to add a parameter, add a defaulted overload. MainWindow's 50 call sites should not need touch for Plan B; that's a Plan C / cutover concern.

### After Phase 3

Phases 5, 6, 7, 8 can largely run in sequence:
- **Phase 5 (Presence UI):** wire `PresenceManager::activeFor()` into the QTreeWidget delegates for the file/session lists. Custom paint delegate for the colored dots. Avatar bar widget for the top-right.
- **Phase 6 (Don't-yank-in-progress):** cell-level dirty tracking + yellow-border decoration when a NOTIFY arrives for an actively-edited cell.
- **Phase 7 (MainWindow wiring):** construct `PostgresConnection`, `NotificationListener`, `PresenceManager`, `ConflictResolver` in the MainWindow constructor after `IdentityManager`. Wire save-path error handling to ConflictResolver.
- **Phase 8 (two-client e2e):** spawn two `DataViewer.exe` instances in tests, exercise simultaneous edits.

## Critical context for the next session

1. **MIP encryption mitigation is real.** Every new `.cpp`/`.h` MUST be created via Python's delete-and-rewrite pattern, NOT `Write`. See CLAUDE.md and the patterns scattered through Plan A's commits. Run `python tools/decrypt_via_copy.py --apply` before EVERY build until the first clean build verifies files are stable.

2. **libpq DLLs are vendored.** `vendor/libpq-16/` has 5 DLLs (~8 MB). Add to PATH when running tests/exe: `export PATH="<repo>/vendor/libpq-16:$PATH"`. The `*.dll` blanket gitignore has a `!vendor/libpq-16/*.dll` exception.

3. **`qsqlpsql.dll` is bundled by the installer** (fix from final review of Plan A). `build_installer.bat` copies it from `C:\Qt\6.10.x\mingw_64\plugins\sqldrivers\`. If running tests locally, add Qt's `plugins/sqldrivers` to PATH OR copy `qsqlpsql.dll` next to the test exe.

4. **Ephemeral Postgres pattern.** Use `tests/start-test-postgres.ps1` for tests (sets `DVE_TEST_PG_CONN` and PATH). Or manually:
   ```bash
   docker run -d --name dve-test-pg -p 5433:5432 \
     -e POSTGRES_DB=dve_test -e POSTGRES_USER=test -e POSTGRES_PASSWORD=test \
     postgres:16
   sleep 8
   # Apply schema (BEGIN..COMMIT only, skip pg_cron tail — vanilla postgres:16 doesn't preload pg_cron):
   sed -n '/^BEGIN;/,/^COMMIT;/p' deploy/postgres/init.sql | docker exec -i dve-test-pg psql -U test -d dve_test
   ```

5. **NOTIFY trigger excludes `settings`.** The `settings` table lacks an `id` column (its PK is `key TEXT`). NOTIFY's trigger function references `NEW.id` which fails on settings. So inserts into `settings` do NOT fire `dataviewer_changes`. Tests that need NOTIFY use `files` instead.

6. **`updated_by` default is `'migration'`.** Schema sets this default for migration rows. Plan B's app code MUST supply a real UUID — relying on the default mints a row attributed to "migration" which silently breaks NOTIFY echo filtering. Spec called this out; Plan C may want to drop the default after migration finishes.

7. **`finalizeSource()` Windows file-rename quirk.** SQLite handles on Windows are released by `QSqlDatabase::removeDatabase(name)`, NOT just `close()`. Pattern: `db.close(); db = QSqlDatabase(); removeDatabase(name); QFile::rename(...)`. Also avoid `QTemporaryFile` for sources you'll rename — it holds a Windows file-share flag that blocks rename even after `close()`.

8. **`QSqlDatabase` reference-clearing pattern.** Same as #7: assign `m_db = QSqlDatabase()` before `removeDatabase` to suppress the Qt "still in use" warning.

9. **Subagents in this session sometimes substituted placeholder tests** for the real ones (caught and corrected for Plan B Phase 1). When dispatching, explicitly say: "the tests MUST exercise the database via real INSERT/UPDATE/SELECT, NOT struct-field smoke tests." And verify the resulting test file before trusting the report.

10. **Plan A's Task 30 (work-machine Synology install verification) is deferred by design.** It can only run on the work machine with real Synology access. Don't try to complete it from a home dev machine.
